## ❓java의 final 키워드 (final/finally/finalize)
모두 같은 final이 들어가지만 다른 용도로 사용됩니다.
- final : 변수, 메서드, 클래스에 사용될 수 있는 제어자이고, 변수에 사용되면 값이 변경될 수 없고 메서드에 사용되면 오버라이딩될 수 없고 클래스에 사용되면 상속할 수 없게 됩니다.
- finally : try-catch 블록에서 사용되는 예약어이고, try블록에서 에외가 발생하느냐와 관계없이 항상 실행되는 코드 블록입니다.
- finalize : 객체가 가비지 컬렉터에 의해 메모리에서 제거되기 직전에 JVM이 마지막으로 호출해주는 메서드입니다.

**➕  컴파일 과정에서, final 키워드는 다르게 취급되나요?** </br>
final 키워드가 붙은 변수는 상수랑 똑같이 취급하고, 메서드는 오버라이딩이 안되기 때문에 오버라이딩 여부를 검사하는 과정이 생략되고, 클래스는 상속이 불가능하기 때문에 자식 클래스를 찾는 과정이 생략됩니다.

</br>

## ❓== 와 Equals() 메서드의 차이는?
자바에서 == 연산자는 두 참조 변수가 같은 객체를 참조하는지 즉, 메모리 주소가 같은지를 비교하고 </br>
equals() 메서드는 객체의 내용이 같은지를 비교합니다.

**➕ 그럼 equals()는 모든 객체에서 값 비교를 하나요?** </br>
아니요. equals()는 Object 클래스에서 상속되며 Object의 기본 구현은 ==와 동일하게 참조 동일성을 비교합니다.
그래서 String, Integer처럼 값 비교가 필요한 클래스만 equals()를 오버라이딩하여 실제 값을 비교합니다.
예를 들어, new 를 이용해 string 객체를 두번 생성하고 equals()로 비교하면 다른 메모리에 할당되어 false가 나올것 같지만 true가 나옵니다.

**➕ 기본형(primitive) 타입에서는 어떻게 비교하나요?** </br>
int, double 같은 기본형 타입은 객체가 아니라 값 자체를 저장하므로 == 연산자가 곧 값 비교입니다. 
기본형에는 메서드가 없기 때문에 equals()는 사용할 수 없습니다.

</br>

## ❓equals(), hashcode() 설명해보세요.
equals()와 hashcode() 모두 자바의 부모 객체인 Object 클래스에 정의되어 있어서 자바의 모든 객체가 상속받습니다.
- equals()는 2개의 객체가 동일한지 검사하기 위해 사용하는데, 2개의 객체가 가리키는 곳에 동일한 메모리 주소일 경우 동일하다고 합니다. (즉 내부적으로 위의 == 를 구현하는 것)
- hashcode()는 실행 중 객체의 유일한 Integer 값을 반환하는데, Object 클래스에서는 객체의 메모리 주소를 반환하도록 되어있습니다.

</br>

## ❓Wrapper class
프리미티브 타입인 기본형은 값 자체를 저장하는 타입이고, 이를 감싸서 객체처럼 사용할 수 있게 만든 클래스를 래퍼클래스라고 합니다. 기본 자료형을 래퍼클래스로 변경하는 것을 Boxing이라고 하고, 반대로 래퍼클래스를 기본 자료형으로 변경하는 것을 UnBoxing이라고 합니다. 

**➕ 왜 사용할까?** </br>
- 컬렉션과 재네릭은 객체 타입만 다룰 수 있어서 기본형 대신 래퍼 클래스를 사용합니다.
- 기본형은 null을 가질 수 없지만, 래퍼클래스는 객체이기 때문에 null 표현이 가능합니다.
- 문자열을 숫자로 변환하는 Integer.parseInt() 같은 유틸리티 메서드가 래퍼클래스에 제공됩니다.

</br>

## ❓new String()과 ""의 차이에 대해 설명해주세요.
new String과 ""리터럴은 둘 다 문자열을 만들지만 객체가 생성/관리되는 방식이 다릅니다. </br>
new String()은 new 키워드를 사용하기 때문에 항상 힙 영역에 새로운 String 객체를 생성합니다. 즉, 같은 값이라도 호출할 때마다 서로 다른 객체가 만들어집니다. </br>
문자열 리터럴 ""은 String Constant Pool(문자열 상수 풀)에 저장됩니다. 이미 동일한 문자열이 존재하면 새로 만들지 않고 기존 객체를 재사용하기 때문에 같은 리터럴은 같은 객체를 참조합니다. 

</br>

## ❓java String이 불변 객체인 이유
- **보안** : String은 비밀번호, 계정 정보, 파일 경로처럼 민감한 데이터를 자주 담습니다. 불변 객체이기 때문에 참조를 공유하더라도 다른 코드에서 내용을 변경할 수 없어 보안상 안전합니다.
- **해시코드 캐싱** : String은 HashMap, HashSet의 키로 자주 사용됩니다. 값이 변하지 않기 때문에 hashCode를 한 번 계산해 캐싱할 수 있고, 값 변경으로 인한 검색 오류를 방지할 수 있습니다.
- **재사용성(String Constant Pool)** : 문자열 리터럴은 String Constant Pool에 저장되어 같은 값이면 하나의 객체를 재사용합니다. String이 가변이었다면 풀에 있는 문자열이 변경될 수 있어 재사용이 불가능했을 것입니다.
- **멀티스레드 안전성** : 여러 스레드가 동시에 같은 문자열을 참조해도 값이 변하지 않으므로 동기화 없이도 안전하게 공유할 수 있습니다.

</br>

## ❓Immutable Object(불변 객체)란?
객체가 생성된 이후 필드 값이 절대 변경되지 않는 객체를 말합니다. 값이 변하지 않기 때문에 멀티스레드 환경에서도 동기화 없이 안전합니다. 

**➕ 불변 객체를 만드는 방법** </br>
- 클래스를 final 로 선언 → 상속을 막아 하위 클래스에서 변경을 막음
- 모든 필드를 private final로 선언 → 외부 접근 및 재할당 차단
- 생성자를 통해서만 값 초기화 → Setter 제공하지 않음
- 가변 객체(List,Map 등)를 필드로 가질 경우 깊은 복사 사용 → 외부에서 참조를 통해 내부 상태가 변경되는 것을 방지

</br>

## ❓Call by Reference와 Call by Value의 차이
**Call by Value**는 값 자체를 복사하여 전달하는 것이라 원래 변수와 새로 만들어진 변수는 다른 메모리에 위치하기 때문에, 원래 변수에 영향을 주지 않습니다. </br>
**Call by References**는 변수의 주소값을 전달하기 때문에, 원래 변수와 새로 만들어진 변수는 같은 메모리에 위치해서 원래 값에 영향을 주게 됩니다. 

**➕ 자바는 ?** </br>
자바는 **Call by Value** 방식만을 사용합니다. </br>
**원시 타입**은 값이 그대로 복사되어 전달되어, 메서드 내부에서 값을 변경해도 원본에는 영향을 주지 않습니다. </br>
**참조 타입**은 객체 자체를 전달하는 것이 아니라 객체의 주소 값을 복사해서 전달합니다. 그래서 메서드 내부에서 객체의 필드를 변경하면 원본 객체에 영향을 줄 수 있습니다. 하지만 메서드 내부에서 새로운 객체를 생성하여 매개변수에 다시 할당하는 경우에는 복사된 참조 값이 다른 객체를 가리키게 되어 원래 변수에는 영향을 주지 않습니다. 

</br>

## ❓클래스변수, 인스턴스변수, 지역 변수
자바에서 변수는 선언 위치나 메모리에 저장되는 위치에 따라 구분됩니다.
- **클래스 변수** : static 키워드를 사용해서 선언하고, 클래스가 메모리에 로드될 때 한번 생성되며 모든 인스턴스가 값을 공유합니다. 메모리의 메서드 영역에 저장되고 객체를 만들지 않아도 클래스명으로 접근이 가능합니다.
- **인스턴스 변수** : 클래스 내부에서 선언되지만 static이 없고, 객체가 생성될 때마다 힙 영역에 할당됩니다. 객체마다 고유한 값을 가지고 인스턴스가 소멸될 때 같이 사라집니다.
- **지역 변수** : 메서드 안에서 선언되어 스택 영역에 저장되고, 메서드가 종료되면 같이 사라집니다. 반드시 초기화 한 후 사용해야하고, 블록 안에서만 유효합니다.

</br>

## ❓String, StringBuilder, StringBuffer의 차이
우선 String과 StringBuilder/StringBuffer의 차이는 </br>
**String**은 불변 객체이기 때문에 한번 생성되면 값이 바뀌지 않고, 값을 변경하면 새로운 String 객체가 생기지만,
StringBuilder/StringBuffer는 가변 객체이기 때문에 문자열 연산 시 새로운 객체를 생성하는 것이 아니라, 내부 버퍼에서 값을 직접 수정합니다. </br>
**StringBuilder**는 동기화를 지원하지 않고, **StringBuffer**는 동기화 지원이 되기 때문에 멀티 스레드 환경에서 안전하지만 락 때문에 속도는 더 느립니다.

</br>

## ❓Java의 Exception에 대해 설명해 주세요.
0으로 나누기, 존재하지 않는 파일 접근, null 참조, 배열 인덱스 초과 등 프로그램 실행 중 발생하는 비정상적인 상황을 객체로 표현한 것입니다. 자바의 모든 예외는 아래와 같이 Throwable을 상속받습니다. </br>
Error는 JVM 수준의 심각한 오류이고, Exception은 개발자가 처리할 수 있는 예외입니다. 
```java
Throwable
 ├── Error  ex) OutOfMemoryError
 └── Exception  
       ├── Checked Exception  ex) IOException,
       └── RuntimeException (Unchecked Exception)  ex) NullPointerException, IllegalArgumentException, IndexOutOfBoundsException
```
**➕ 예외 처리를 하는 세 방법에 대해 설명해 주세요.** </br>
1. 예외가 발생할 가능성이 있는 코드를 try 블록 안에 작성하고, 예외가 발생하면 catch 블록으로 넘어가 예외를 처리하는 방법 - finally는 예외 발생 여부와 상관없이 항상 실행
2. throws를 사용해서 메서드 내부에서 예외처리를 하지 않고, 호출한 쪽으로 예외를 전달하는 방법
3. throw를 사용해서 상황에 따라 직접 예외 객체를 만들어 던지는 방법

**➕ CheckedException, UncheckedException 의 차이에 대해 설명해 주세요.** </br>
CheckedException은 컴파일 시점에 확인되는 예외이고 반드시 예외 처리를 해야하지만
UncheckedException은 실행 중 발생하는 예외이고 따로 예외처리를 하지 않아도 됩니다.

**➕ 예외 처리가 성능에 큰 영향을 미치나요? 만약 그렇다면, 어떻게 하면 부하를 줄일 수 있을까요?** </br>
예외 처리는 예외가 발생하지 않는다면 성능에 큰 영향을 주지 않습니다. 하지만 예외가 발생하면 스택 트레이스 수집과 언와이딩 때문에 비용이 발생하고 성능 저하로 이어질 수 있습니다. </br>
부하를 줄이는 방법은 </br>
예외는 예외적인 상황에만 사용하고 정상 흐름은 if 검증이나 Optional 타입으로 처리하고 </br>
자주 호출되는 경로에서는 예외가 발생하지 않도록 사전 검증을 하고 </br>
로깅은 최소화하거나 샘플링 방식으로 제한하고, 필요시 스택 트레이스를 비활성화한 경량 예외를 사용할 수 있습니다. </br>
즉 예외는 제어 흐름을 위한 수단이 아니라 진짜 예외 상황에서만 사용하자가 핵심입니다.
