## ❓동기화와 비동기화의 차이 (Syncronous vs Asyncronous)
**동기 방식**은 하나의 작업이 끝날 때까지 기다린 후 다음 작업을 수행하는 방식입니다. 즉 호출한 쪽이 결과를 받을 때까지 제어권을 넘기지 않고 기다립니다. </br>
**비동기 방식**은 작업을 요청한 뒤 결과를 기다리지 않고 다음 작업을 계속 수행하는 방식입니다. 결과는 나중에 콜백, Future, CompletableFuture 등을 통해 받습니다.

**➕ 블로킹/논블로킹과 다른 개념인가요?** </br>
동기/비동기는 결과를 기다리느냐의 문제이고, 블로킹/논블로킹은 스레드가 멈추느냐의 문제입니다. </br>
블로킹(Blocking)은 작업이 끝날 때까지 스레드가 멈추고, 논블로킹(Non-Blocking)은 작업이 끝나지 않았더라도 스레드는 멈추지 않고 계속 실행됩니다.  

**➕ 비동기와 멀티스레드는 같은 개념인가요?** </br>
아닙니다. 비동기는 작업 결과를 기다리지 않는 방식이고, 멀티스레드는 스레드가 여러개인 실행 구조입니다. </br>
싱글 스레드에서도 비동기가 가능하고 멀티스레드 환경에서도 동기 방식으로 동작할 수 있습니다. 

**➕ 자바에서 비동기를 어떻게 구현하나요?** </br>
자바에서는 CompletableFuture, ExecutorService, @Async 등을 사용해 비동기 처리를 구현할 수 있습니다. </br>
작업을 별도 스레드에서 실행하고 결과는 나중에 처리하는 방식입니다.

</br>

## ❓volatile vs atomic
- **volatile** : 가시성을 보장하는 키워드입니다. 여러 스레드가 같은 변수를 공유할 때, CPU 캐시가 아닌 메인 메모리에서 직접 읽고 쓰도록 강제합니다. 즉, 한 스레드가 값을 변경하면 다른 스레드가 즉시 그 변경을 볼 수 있습니다. 하지만 원자성을 보장하지 않습니다. 예를 들어, count++ 같은 연산은 read->add->write 세 단계로 나뉘기 때문에 중간에 다른 스레드가 끼어들 수 있습니다. 
- **atomic** : Atomic 클래스는 java.util.concurrent.atomic 패키지에 포함된 클래스입니다. 대표적으로 AtomicInteger, AtomicLong 등이 있으며, 가시성과 원자성을 모두 보장합니다. 내부적으로 CAS(Compare-And-Swap) 연산을 사용하여 락 없이 thread-safe한 연산을 수행합니다.

**➕ CAS란 무엇인가요?** </br>
Compare-And-Swap의 약자입니다.
1. 현재 메모리 값이 내가 예상한 값과 같은지 비교하고
2. 같으면 새 값으로 변경
3. 다르면 다시 시도합니다.
이 방식은 락을 사용하지 않기 때문에 낙관적 락(Optimistic Lock) 방식이라고 볼 수 있습니다.

**➕ Atomic의 단점은 무엇인가요?** </br>
실패 시 재시도(Spin)로 인해 CPU 사용량이 증가할 수도 있고, ABA 문제가 발생할 수도 있습니다. </br>
ABA 문제는 값이 A->B->A로 변경되면 겉보기에는 변하지 않은 것처럼 보이는 문제입니다. 그래서 AtomicStampedReference 같은 버전 기반 비교 방식을 사용하여 해결합니다.

**➕ synchronized와의 차이** </br>
synchronized(동기 + 블로킹)는 락을 획득하지 못하면 스레드가 대기하는 블로킹 방식이고, Atomic은 논블로킹 방식입니다.

</br>

## ❓Synchronized 키워드에 대해 설명해 주세요.
멀티스레드 환경에서 공유 자원에 동시에 접근하지 못하도록 막는 동기화 키워드입니다. 임계 구역에 한 번에 하나의 스레드만 들어가도록 보장해서 race condition을 방지합니다. 동기 방식이며, 락을 얻지 못하면 스레드는 대기하는 블로킹 방식입니다.

**➕ synchronized가 붙는 위치에 따른 차이** </br>
- 인스턴스 메서드 : 객체 단위 락입니다. 같은 객체에 대해 하나의 스레드만 접근할 수 있습니다.
- static 메서드 : 클래스 단위 락입니다. 모든 인스턴스가 공유하는 클래스 전체에 대해 하나의 락을 사용합니다.
- 블록 수준 : 특정 코드 영역만 잠급니다. 필요한 부분만 보호해서 성능상 더 효율적입니다.

**➕ 효율적인 코드 작성 측면에서, Synchronized는 좋은 키워드일까요?** </br>
항상 좋은 것은 아닙니다. 락을 획득하고 해제하는 비용이 있고, 스레드가 전환 시 context swiching 비용이 발생합니다. 
다른 스레드가 수정할 수 있다는 가정으로 항상 락을 먼저 걸고 작업하기 때문에 경쟁이 많을수록 성능 저하가 발생할 수 있습니다.

**➕ Synchronized 를 대체할 수 있는 자바의 다른 동기화 기법에 대해 설명해 주세요.** </br>
- **ReentrantLock** : 내가 락을 언제 걸고 풀지 정할 수 있고, 일정 시간만 락 획득을 시도하거나 특정 조건을 만족할 때만 스레드를 깨우는 동작같이 세밀한 제어가 가능합니다.
- **ReadWriteLock** : 읽기는 여러 스레드 허용, 쓰기는 단독 잠금으로 읽기가 많은 환경에서 유리합니다.
- **Atomic** : CAS 기반으로 동작해서 락을 걸지 않고도 thread-safe한 연산을 할 수 있습니다. 단일 변수 연산에 적합합니다.
- **ConcurrentHashMap** : Map을 여러 조각으로 나누어 조각마다 락을 걸어, 여러 스레드가 서로 다른 조각을 동시에 수정할 수 있도록 합니다.

**➕ Thread Local에 대해 설명해 주세요.** </br>
스레드마다 독립적인 변수 공간을 제공하는 클래스입니다. 스레드 간 공유하지 않기 때문에 동기화가 필요 없습니다. 예를 들어 사용자 세션 정보 등을 저장할 때 사용합니다.
다만, 스레드 풀 환경에서는 remove()를 호출하지 않으면 이전 값이 남을 수 있어 주의가 필요합니다.

</br>

## ❓자바 다이나믹 프록시에 대해 설명해 주세요.
자바 다이나믹 프록시는 메서드 호출을 프록시 객체가 가로채서 공통 기능을 수행한 뒤 실제 객체를 호출하는 방식입니다. </br>
이 과정 덕분에 개발자는 로깅/트랜잭션 처리/보안 검사 같은 횡단 관심사(공통 로직)를 핵심 비지니스 로직과 분리할 수 있고, 코드 중복을 줄일 수 있습니다. </br>
또한 하나의 프록시로 여러 구현체에 공통 기능 적용이 가능하기에 공통 기능이 바뀌더라도 프록시 클래스만 수정하면 되므로 유지보수가 쉬워집니다. </br>
하지만 자바 기본 다이나믹 프록시는 인터페이스 기반으로 동작하기에 인터페이스가 없는 클래스는 JDK 다이나믹 프록시로 만들 수 없습니다. 
그래서 스프링 AOP는 내부적으로 인터페이스가 있으면 JDK 다이나믹 프록시, 없으면 CGLIB 프록시를 사용합니다. 
CGLIB는 클래스를 상속받아 서브클래스를 만들어 프록시 객체를 생성합니다. 

</br>

## ❓리플렉션이란?
리플렉션은 컴파일 시점에 구체적인 타입을 몰라도 런타임에 클래스의 정보(필드, 메서드, 생성자 등)에 접근할 수 있게 해주는 자바 API입니다. 
- **장점** : 런타임에 동적으로 객체를 생성할 수 있고, 접근 제어자와 관계없이 필드나 메서드에 접근할 수 있어 유연성이 높습니다.
- **단점** : 캡슐화가 깨지고 컴파일 시점에 타입을 체크할 수 없으며, 런타임에 클래스 정보를 탐색하고 접근하기 때문에 일반 메서드 호출보다 느립니다.

**➕ 보안적인 문제가 있을 가능성이 있어보이는데, 실제로 그렇게 생각하시나요?** </br>
무분별하게 사용하면 보안 문제가 발생할 수 있습니다. </br>
접근 제어자와 관계없이 private 필드나 메서드에 접근할 수 있어 캡슐화를 깨뜨릴 수 있습니다. 
특히 외부 입력과 결합되거나 역질렬화 과정에서 악의적인 클래스가 로딩될 경우, 의도치 않은 객체 생성이나 메서드 실행이 발생할 수도 있습니다. </br>
그래서 리플렉션을 악용하지 못하도록 record를 적극 사용하고, JPA 기본 생성자를 protected로 제한하고, 외부 입력 검증을 강화하는 등 방어적인 코드를 작성해야 한다고 생각합니다.

**➕ 리플렉션은 언제 사용하나요?** </br>
규모가 작은 프로그램에서는 컴파일 시점에 사용될 객체와 의존관계를 모두 파악할 수 있지만 규모가 큰 개발에서는 다 파악하기 어려운데, 이때 리플렉션을 사용하면 동적으로 클래스를 만들어서 의존 관계를 맺어줄 수 있습니다. </br>
Spring은 실행 시점에 @Controller, @Service, @Repository 같은 어노테이션이 붙은 클래스를 스캔합니다. 그리고 리플렉션을 이용해 해당 클래스의 객체를 생성하고, 필요한 의존성을 주입한 뒤 Bean으로 등록해 관리합니다.
즉, 개발자가 직접 객체를 생성하지 않아도, 리플렉션을 통해 자동으로 Bean이 생성되고 컨테이너에서 관리됩니다.
