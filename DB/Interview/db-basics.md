## ❓데이터베이스 정규화에 대해서 설명해보세요.
하나의 릴레이션에 하나의 의미만 존재하도록 릴레이션을 분해하는 과정이며 데이터 일관성, 최소한의 중복, 최대한의 데이터 유연성을 위한 방법입니다.
- **1NF**(제 1정규형) : 테이블 컬럼에는 하나의 값만 → 원자성
- **2NF**(제 2정규형) : 1정규형을 만족하고, 복합키 중 일부에만 종속된 컬럼은 따로 분리 → 일부 키에만 의존하지 않도록
- **3NF**(제 3정규형) : 2정규형을 만족하고, 기본키가 아닌 컬럼이 다른 컬럼에 종속되어 있으면 분리 → 컬럼이 컬럼에 의존하지 않도록
- **BCNF**(Boyce-Codd) : 3정규형을 만족하고, 모든 결정자가 후보키가 되도록 함 → 키 아닌 컬럼이 다른걸 결정하지 않도록

**장점** : 데이터베이스 변경 시 이상 현상이 발생하는 문제를 해결하고, 구조 확장 시 변경을 최소화합니다. </br>
**단점** : 테이블을 많이 분해하면 테이블 간의 연산(Join)에서 시간이 많이 소비되어 성능 저하가 발생할 수 있습니다.

**➕ 정규화를 하지 않을 경우, 발생할 수 있는 이상현상에 대해 설명해 주세요.** </br>
1. **삽입 이상** : 불필요한 데이터가 없으면 필요한 데이터도 저장 불가 → 학생+과목 테이블에서 학생이 없으면 과목을 등록할 수 없는 경우
2. **갱신 이상** : 중복된 데이터 중 일부만 수정되어 데이터 불일치 발생 → 같은 학생의 학과 정보가 여러행에 있을 때 한 행만 수정되는 경우
3. **삭제 이상** : 불필요한 데이터를 삭제했는데 중요한 정보까지 삭제 → 어떤 학생의 마지막 과목 정보를 삭제했더니 기본 정보까지 사라지는 경우

**➕ 정규화가 무조건 좋은가요? 그렇지 않다면, 어떤 상황에서 역정규화를 하는게 좋은지 설명해 주세요.** </br>
정규화는 데이터 무결성 측면에서는 매우 좋은 선택이지만 성능 측면에서 항상 최선은 아닙니다. 
정규화가 심해지면 테이블이 많아지고, JOIN이 많아지며, 조회 성능이 떨어질 수 있습니다. </br>
**역정규화**는 성능 개선을 위해 의도적으로 중복을 허용하는 설계입니다.
- 조회가 압도적으로 많은 경우 : 메인 페이지, 통계, 대시보드처럼 읽기 위주 서비스
- JOIN 비용이 너무 큰 경우 : 항상 함께 조회되는 데이터라면 같은 테이블에 미리 저장
- 과거 데이터 보존이 중요한 경우 : 주문 테이블에 상품명과 가격을 함께 저장 → 상품 정보가 바뀌어도 과거 주문 내역은 유지 가능

</br>

## ❓Key에 대해 설명해주세요
- **슈퍼키**(Super key) : 행을 유일하게 식별할 수 있는 속성 집합, 유일성O/최소성X
- **후보키**(Candidate key) : 최소성을 만족하는 슈퍼키, 유일성O/최소성O
- **기본키**(Primary Key) : 후보키 중 선택된 키
- **대체키** (Alternate Key) : 후보키 중 기본키로 선택되지 않은 키
- **외래키** (Foreign Key) : 다른 테이블의 기본키를 참조하는 키

**➕ 기본키는 수정이 가능한가요?** </br>
이론적으로 UPDATE가 가능합니다. 하지만 기본키를 변경하면 이 키를 참조하는 모든 외래키도 영향을 미치기 때문에 CASCADE가 없으면 참조 무결성 오류가 발생합니다. 그래서 일반적으로는 절대 변하지 않는 값을 PK로 설정합니다.

**➕ MySQL은 기본키 없이도 테이블이 생성되는데 왜 가능한가요?** </br>
InnoDB는 클러스터드 인덱스 구조로 데이터를 PK 순서대로 디스크에 정렬하여 저장하기 때문에 반드시 PK가 필요합니다. </br>
사용자가 PK를 만들면 그것을 사용하고 </br>
PK가 없으면 사용자가 만든 `UNIQUE + NOT NULL` 컬럼 중 하나를 대신 사용하거나 </br>
그것도 없으면 6바이트 크기의 숨겨진 row_id를 자동 생성합니다. </br>
이 row_id는 자동 증가하고 / 외부에서 보이지 않으며 / 업데이트가 불가하고 / 삭제되면 재사용되지 않습니다.

**➕ 외래키 값은 NULL이 들어올 수 있나요?** </br>
가능합니다. 외래키 제약은 값이 존재할 경우 부모 테이블에 해당 PK가 있어야 한다는 의미입니다.
- FK = NULL → 부모 없는 자식 허용 (optional 관계)
- FK = 값 존재 → 반드시 부모가 존재해야 함 (mandatory 관계)
따라서 관계 성격에 따라 FK를 NOT NULL로 설정할지 결정합니다.

**➕ UNIQUE 키워드가 붙으면 성능이 어떻게 달라지나요?** </br>
UNIQUE 제약을 선언하면 DBMS가 자동으로 유니크 인덱스를 생성하기 때문에 해당 컬럼을 조회할 때 인덱스를 사용해 빠르게 탐색할 수 있습니다. 반면 인덱스가 없는 일반 컬럼은 조건 검색 시 테이블 전체를 스캔하게 되어 성능이 더 느릴 수 있습니다.

</br>

## ❓Schema가 무엇인가요?
스키마는 데이터베이스의 구조와 제약 조건을 정의한 설계도입니다.
어떤 테이블이 있는지, 컬럼과 데이터 타입은 무엇인지, 테이블 간 관계는 무엇인지, PK/FK/UNIQUE 같은 제약 조건은 무엇인지를 미리 정의해둔 구조입니다. DBMS는 데이터를 저장·조회·수정할 때 이 스키마를 기준으로 동작합니다.

**➕ Schema의 3계층에 대해 설명해 주세요.** </br>
데이터베이스는 데이터 독립성을 보장하기 위해 3계층 구조로 나뉩니다.
- **외부 스키마(External Schema)** → 사용자 관점
   - 사용자나 응용 프로그래머가 개인의 입장에서 필요로 하는 데이터 구조
   - 같은 DB라도 사용자별로 다른 화면을 제공할 수 있고, 하나의 외부 스키마를 여러개의 응용 프로그램이나 사용자가 공유 가능
   - ex) 학생과 관리자가 보는 데이터가 다름
- **개념 스키마(Conceptual Schema)** → 전체 논리 구조
   - 데이터베이스 전체의 논리적 구조
   - 테이블, 관계, 제약 조건 정의
   - ERD 설계 단계에서 정의되는 구조
- **내부 스키마 (Internal Schema)** → 물리적 저장 구조
   - 실제 디스크에 어떻게 저장되는지 정의
   - 인덱스 구조, 페이지 단위 저장 방식 등
   - ex) id 컬럼에 B+Tree 인덱스, InnoDB 페이지 구조
 
</br>

## ❓RDBMS와 NoSQL의 차이에 대해 설명해 주세요.
**RDBMS**는 관계형 데이터베이스로 테이블 간의 관계를 기반으로 데이터를 관리합니다. column과 row 구조를 가지며 복잡한 쿼리와 JOIN을 효율적으로 처리할 수 있고 ACID 트랜잭션을 강하게 보장합니다. </br>
**NoSQL**은 비관계형 데이터베이스로 Key-Value나 Document 같은 다양한 데이터 모델을 사용합니다. 정해진 스키마가 없어서 구조가 자주 바뀌는 서비스에 적합하고, 여러 서버를 묶는 수평 확장이 쉬워 대규모 트래픽 처리에 유리합니다. 

**➕ NoSQL의 강점과, 약점이 무엇인가요?** </br>
- **강점** : 수평 확장이 쉬워 대규모 트래픽 처리에 적합하고 스키마가 유연해 구조 변경이 잦은 서비스에 유리합니다. 또한 Key-Value 구조나 메모리 기반 처리로 속도가 빠릅니다.
- **약점** : ACID 보장이 약해서 강한 정합성이 필요한 금융·결제 시스템에는 적합하지 않을 수 있고, 복잡한 JOIN을 지원하지 않아 데이터 중복을 감수해야 하는 단점이 있습니다. 또한 표준 쿼리 언어가 없어 DB마다 문법이 다릅니다.

**➕ RDBMS가 NoSQL보다 부하가 더 걸릴 수 있는 이유가 무엇일까요?** </br>
1. 강한 ACID 보장을 위해 트랜잭션 처리와 락 관리가 필요해 동시성이 높으면 병목이 발생할 수 있습니다. </br>
2. 여러 테이블을 연결하는 JOIN 연산은 대용량 데이터에서 비용이 큽니다. </br>
3. 외래키나 UNIQUE 같은 무결성 제약 조건 검사가 매 요청마다 발생해서 성능 부담이 생길 수 있습니다.
